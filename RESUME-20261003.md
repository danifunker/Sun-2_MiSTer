### 5. The keyboard bell (small)

  0x03 bell off -> `bell` (unconnected: `.bell ()` in `Sun-2.sv`).  0x0A/0x0B

  when enabled, as a Type 3 keyboard does.

  domain (the framework's `CLK_AUDIO`), with `bell` crossed in by two flops.
  Find the real beeper's pitch before choosing one (Type 3 keyboard docs /
  `sundev/kbd.c`, `KIOCCMD`); a square wave softened to avoid harshness.
  Maybe an OSD volume (off / low / high).
* Test: unit bench for the tone gate; on the board, SunView's `window_bell`
  or a tiny C program doing `ioctl(fd, KIOCCMD, &KBD_CMD_BELL)` on `/dev/kbd`.

### 6 + 7. Machine identity and networking (one Main_MiSTer change; plan first)

The core today: the on-board 82586 (`rtl/sun2-vme/sun2_ethernet.sv`, vendored
`rtl/vendor/wish82586`) runs with its MII tied off in `Sun-2.sv` (`mii_rxd
4'd0` ...); SunOS attaches `ie0` and sees no carrier.  The ID PROM
(`rtl/sun2-common/idprom.v`) is constants: every machine is `8:0:20:1:6:E0`,
serial 3442.

Model to copy: **upstream Main_MiSTer `support/next/next_enet.cpp`** (read
2026-10-03).  A 64 KiB mailbox in DDR3 at ARM 0x1FF00000 (the A2065's window):
MAGIC (FPGA-written), TX_WPTR (FPGA), RX_WPTR (daemon), RX_RPTR (FPGA),
GUEST_MAC (bit 63 valid, 47:0 address), 4 TX and 4 RX slots of 2 KiB (u64
length, then the frame).  Started by Main when the core name matches
(`user_io.cpp`: `if (is_next()) next_enet_start()`), polled each loop, mode
from an OSD status option (`mode_from_status()`: off / eth0 / eth1 / macvlan /
tap), host side shared with the A2065 module (`ethernet_open`, macvlan with
the guest's MAC, ...).

Plan:
1. **Main_MiSTer** (the user's fork; a PR upstream is the user's call):
   `support/sun2/sun2_enet.cpp` cloned from the NeXT one -- own MAGIC
   ("SUN2ETH1"), core-name gate "Sun-2", same modes.  **Item 6 rides on it**:
   the module also writes a host-derived address (Sun OUI 08:00:20 + the host
   NIC's low three octets, as MacQuadra800's `mac_eth` does with its own OUI)
   into a mailbox slot the core reads -- or sends it as a small download
   before `boot0.rom`, since the core holds reset until the PROM arrives and

2. **Core, identity:** `idprom.v` takes ETH3..5 (and maybe the serial) at run

3. **Core, network:** a DDR3 Avalon master on the `DDRAM_*` port (unused, tied

### 8. Colour: the cgtwo (big; plan first -- research done 2026-10-03)

**Resolution: 1152x900, the same raster as the mono screen.**  The user asked
whether colour runs at 640x480: that is the **cgone** (Sun-1 Color,
`FBTYPE_SUN1COLOR`, 640x480x8), a MultiBus board -- 4.0.3 GENERIC has `cgone0
at mbmem ? csr 0xec000`, and `mbmem` exists only on MultiBus Sun-2s.  The VME
board, and the user's choice, is the **cgtwo** ("Sun-2 color board",
`FBTYPE_SUN2COLOR`): its status register's resolution field is 0 = 1152x900
or 1 = 1024x1024 (`cg2reg.h`), nothing smaller.  SunView takes the size from
the driver (`FBIOGTYPE`), so 1152x900 it is, shown 1:1 at 1080p like bwtwo.

What has to exist, from the sources (`sunos-34-src` `sun/sys/sundev/cgtwo.c`,
`sun/mon3/dev/cg2reg.h`; `sunos-414-src` `usr.lib/libpixrect/cg2/*.c`,
`pixrect/cg2reg.h`, `mem/memreg.h` -- all via `gh api`; scratch copies are
not kept):

* **Address map** (VME A24 at 0x400000, 4 MiB): 0x000000 plane-mode memory
  (8 bit planes, 16-bit words, 1152/16 words a line), 0x100000 pixel-mode
  memory (a byte a pixel), 0x200000 rop-mode memory (`ropio`: the same
  pixels/planes through the raster-op chips), 0x300000 control registers --
  status, plane mask `ppmask`, `ropcontrol[]` (one `memropc` per plane plus
  `CG2_ALLROP`), zoom/word pan/pixel pan/variable zoom -- and 0x310000 the
  colour map (red, green, blue x 256; `update_cmap` copies it at retrace).
* **Status register**: resolution (bits 11:8), `retrace` (must really
  toggle -- the PROM *and* the kernel probe spin on its edges), interrupt
  pending/enable (level 4, vector 0xA8), `ropmode` (3 bits), `update_cmap`,
  `video_enab`.
* **The kernel probe needs the raster-op chips**, so "frame buffer first,
  rop later" works only for the PROM: `cgtwoprobe()` sets `ppmask` 0xFF,
  `mrc_op` 0xCC (SRC) on ALLROP, `ropmode` SWWPIX, masks 0, width/opcount 0,
  shift `1<<8`, primes `source2`, writes pixel 0xFF through `ropio`, sets
  `ppmask` 0xAA, writes 0, and needs **0xAA** back.  Then it pokes the
  double-buffer word's wait bit (0x200) to tell cg2 from cg3 -- be a cg2.
* **SunView's drawing (libpixrect `cg2_rop.c`, `cg2_vec.c`, `cg2_batch.c`,
  `cg2_getput.c`) uses ropmodes PRWWRD, SRWPIX, PWWWRD, SWWPIX, PRRWRD,
  PWRWRD, plus `ppmask`, function, shift, width/opcount and pattern** -- the
  `memropc` has to be complete.  libpixrect's own source is the specification
  of how it is driven; `mem/mem_rop.c` is a software rasterop to check
  results against.  Worth looking on Bitsavers for the Sun-2 Color Graphics
  board manual for the chip's exact semantics.
* **The PROM's colour console** (`doc/prom/README.md`): colour jumper = bit 9
  of the video control register (0xEE3800); `_init_scolor` touches status,
  the maps, zoom/pans, then draws the console in **plane 0** with an
  alternating colour map.
* **Kernels:** 4.0's and 4.0.3's GENERIC have `cgtwo0 at vme24 ? csr 0x400000
  priority 4 vector cgtwointr 0xa8` (and `cg2_rop` compiled in); **4.0.3
  GENERIC_SMALL has no colour device** -- the 1 GB disk needs 4.0.3's GENERIC
  (`boot/vmunix` in the 4.0.3 tape's volume 1, file 8) as its `/vmunix`.  The
  user's 4.0 disk already runs GENERIC.

Design sketch to settle in the plan:
* **Store pixels chunky, a byte each** (1,036,800 bytes).  Pixel mode is then
  direct, and a plane-mode or rop word (16 pixels x 8 planes) is one 16-byte
  read-modify-write -- the ROP engine works a 16-pixel group at a time,
  every plane in parallel, per `ppmask`.  Scan-out reads bytes through a
  256x24 colour LUT.
* Where: SDRAM beside main memory (bandwidth: 62 MB/s of scan-out at 60 Hz
  on top of the CPU) vs DDR3 (MiSTer's `MISTER_FB` 8bpp + palette offloads
  scan-out to ascal, but the CPU's path to DDR3 is slower).  Measure before
  choosing.
* Mono and colour together, as on a real 2/160: show the cgtwo when present
  and `video_enab`, the bwtwo otherwise; an OSD switch for the colour jumper.
* Steps: (1) registers, colour map, pixel/plane memory, scan-out, the PROM's
  colour console; (2) the `memropc` engine with Verilator benches driven the
  way libpixrect drives it, checked against a software rasterop, until the
  kernel probe passes; (3) SunView in colour on the board; (4) speed.

* The checkout is CRLF (`core.autocrlf=true`): `sed` anchors miss `\r`.  A
  Python heredoc in the Bash tool loses `\\`; edit Makefile recipes with the
  Edit tool.
* `rtl/vendor/*` are unmodified upstream copies; `rtl/patched/` holds the one
  patched file.
* Board: check `/tmp/CORENAME` before typing.  `tools/mister_keys.py`: `|` is
  Return, `{PIPE}` types a pipe; `{M dx dy}`, `{ML}`/`{MR+}`/`{MR-}` the
  mouse -- keep a press and its release in one run.  Typing during boot is
  lost: wait for `login:`.  SunView sends keys to the window under the
  pointer.  Screenshots don't show the OSD; they are 1160x904 at 1080p.
* Loading a core through an MGL changes the remembered disk
  (`config/Sun-2.s0`).
* `Reboot failed...help!` on `/usr`: `umount /usr`, `fsck -y /dev/rsd0g`,
  `reboot` (never `sync`/halt there).
* SunOS facts: the Sun-2 disk ceiling is 1 GiB; 4.0.3 tapes are upgrade-only;
  `times()` is in sixtieths; a user bus error is always SIGSEGV.
