## Next: what the colour scan-out costs the CPU

**The user wants this measured first**, then mitigated if it can be felt.  The
colour picture is 1152x900x60 Hz, 62 MB/s.  This SDRAM controller (rtl/sdram.sv,
BL8 reads, CAS 2, ~100 MHz) takes about 13-15 clk_mem clocks per 16-byte
burst, single bursts only.  So scan-out is about half the SDRAM's time, and the
CPU's cache misses (sun2_cached_fifo_bridge, 8 KiB, `IDX = 9`) and the colour
engine's line reads wait behind it.

**Measure, both ways, colour On against Off** (`O[12]`; a reset after changing):

1. **On the board.**
   * Time CPU- and memory-bound work with `/bin/time`, quoting `user`, not
     `real` (CLAUDE.md explains).  Candidates: a shell or awk loop; `sum
     /vmunix`; `dd if=/vmunix of=/dev/null bs=8k`; a compile with `cc` if the
     disk has the compiler.  `tools/memloop.s`, `tools/patwr.c` and
     `tools/memchk.c` are earlier benchmarks.
   * Run `ps -aux` first: a runaway cron once doubled every `real`.
   * Run each pair interleaved, as On, Off, On, Off, not all On then all Off.
2. **In simulation**, which can say why.  In `tb_emu`, count clk_mem cycles per
   client in `sun2_mister_sdram`: busy serving the colour scan-out, the CPU, the
   engine; and how long a CPU request waits from `wb_cyc&wb_stb` to its
   service.  Do this with the PROM running and colour On and Off, and report
   the distribution, not just the mean.  Count how often `cs_urgent` priority
   is taken, and whether a line was ever late (a check: the line wasn't
   complete when its display began).
3. **Interactively:** SunView startup time, and scrolling a shelltool, On
   against Off.

**If it is felt, the options, in the order to try:**

* **A bigger CPU read cache in BRAM.**  This is the BRAM answer to "make it
  feel unimpacted".  The framebuffer itself cannot go in BRAM: it is 1 MiB, and
  only ~366 M10K (~450 KB) are free.  But the CPU's own cache can grow:
  `sun2_cached_fifo_bridge`'s `IDX` from 9 (8 KiB) to 12 (64 KiB) is about 60
  M10K.  Fewer misses means fewer waits behind scan-out.  Check timing after:
  the tag compare is on the hit path.
* **Back-to-back BL8 reads in rtl/sdram.sv for the scan-out** (pipeline the
  next READ during the burst).  This cuts scan-out from ~58% of SDRAM time to
  ~31%.  It is risky: sdram.sv is the hardware-tested controller from
  MacQuadra800, and tb_mister_sdram plus its chip model would have to cover the
  new path.
* **Fairer or smarter arbitration**: serve the CPU first unless the scan-out
  is urgent.  Measure before changing.
* A lower raster rate (the scaler keeps HDMI at 60 Hz) would halve the cost,
  but changes the analogue output and the retrace rate.  Last resort; ask.

Whatever changes, re-run `tb_cgtwo`, `tb_emu` (colour On and Off), the rest of
`make -C tb/verilator`, and a board boot to `suntools`.

## Gotchas met this session

* **CRLF files.** Most RTL, `Sun-2.sv` and `README.md` are CRLF, and the Edit
  tool's anchors miss there.  Edit them with a small Python script that
  normalises line endings, replaces exact strings, asserts one match each, and
  restores the endings.  The session used `rep.py` in its scratchpad;
  recreate it.  A Python heredoc in the Bash tool loses `\\` and turns `\n`
  into newlines, so write such scripts with the Write tool.
* **WSL.**
  * Run from Git Bash as `MSYS_NO_PATHCONV=1 wsl -d Ubuntu-24.04 -- bash
    /mnt/c/.../script.sh`.  Env vars don't cross; pass arguments.
  * `/tmp` writes from a WSL command were once lost; keep logs under `build/`.
  * A `run_tb_emu` file held open on the Windows side can't be deleted.
* `tb_emu` takes about 6 minutes for 1.5 s simulated, including the Verilator
  build.  The banner is at about 1.1 s.
* **Board.**
  * `mister_keys.py` has no `{&&}`: type `&&` plainly.  A crashed run leaves a
    half-typed line, so clear it before retyping.
  * The SunView console window shows only three lines; take a screenshot after
    the command finishes.
  * Screenshots: a helper script that ssh's `sleep N; echo screenshot >
    /dev/MiSTer_cmd`, then scp's the newest PNG.
* SunOS 4.0.3 fscks every filesystem every boot: about 3 minutes to `login:`
  on the 1 GB disk.
* The 4.0.3 tape: volume 1 file 8 (0-based) is `boot/` with GENERIC
  `boot/vmunix`, the same file the upgrade leaves as `/vmunix.orig`.
