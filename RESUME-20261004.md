## Next: 8, colour (the cgtwo)

The board is the Sun-2 Color board, `FBTYPE_SUN2COLOR`, 1152x900x8 at VME A24
0x400000 -- the facts gathered so far are under "cgtwo reference" below.  The
hard part is the **raster-op chips**: the kernel's probe needs them, SunView
drives them for nearly everything, and **no manual for them has turned up**
(Bitsavers has none; its Graphics Processor manuals describe the GP, not the
board).  TME's `machine/sun/sun-cgtwo.c` (Matt Fredette, BSD-style licence:
reference only, do not copy) emulates only SWWPIX with two functions -- enough
for the probe and a console, not for SunView.  So the specification has to be
derived from the software that drives the chips, and checked before any RTL.

## cgtwo reference (research 2026-10-03)

**Resolution: 1152x900, the same raster as the mono screen.**  640x480 colour
is the **cgone** (Sun-1 Color), a MultiBus board -- `cgone0 at mbmem`, and
`mbmem` exists only on MultiBus Sun-2s.  The cgtwo's resolution field is 0 =
1152x900 or 1 = 1024x1024, nothing smaller; SunView takes the size from the
driver.

* **Address map** (VME A24 at 0x400000, 4 MiB): 0x000000 plane-mode memory
  (8 bit planes, 16-bit words, 1152/16 words a line), 0x100000 pixel-mode
  memory (a byte a pixel), 0x200000 rop-mode memory (`ropio`: the same
  pixels/planes through the raster-op chips), 0x300000 control registers --
  status, plane mask `ppmask`, `ropcontrol[]` (one `memropc` per plane plus
  `CG2_ALLROP`, each with a "prime" copy at +0x800 per TME), zoom/word pan/
  pixel pan/variable zoom -- and 0x310000 the colour map (red, green, blue x
  256; `update_cmap` copies it at retrace).  A `memropc`: dest, source1,
  source2, pattern, mask1, mask2, shift, op, width, opcount, decoderout.
* **Status register**: resolution (bits 11:8), `retrace` (must really
  toggle -- the PROM *and* the kernel probe spin on its edges; TME fakes one
  every few reads), interrupt pending/enable (level 4, vector 0xA8),
  `ropmode` (3 bits), `update_cmap`, `video_enab`.
* **The kernel probe**: `cgtwoprobe()` sets `ppmask` 0xFF, `mrc_op` 0xCC (SRC)
  on ALLROP, `ropmode` SWWPIX, masks 0, width/opcount 0, shift `1<<8`, primes
  `source2`, writes pixel 0xFF through `ropio`, sets `ppmask` 0xAA, writes 0,
  and needs **0xAA** back; then it pokes the double-buffer word's wait bit
  (0x200) to tell cg2 from cg3 -- be a cg2.
* **The PROM's colour console** (`doc/prom/README.md`): colour jumper = bit 9
  of the video control register (0xEE3800); `_init_scolor` touches status,
  the maps, zoom/pans, then draws the console in **plane 0** with an
  alternating colour map.
* **Kernels:** 4.0's and 4.0.3's GENERIC have `cgtwo0 at vme24 ? csr 0x400000
  priority 4 vector cgtwointr 0xa8` (and `cg2_rop` in the kernel too); 4.0.3
  GENERIC_SMALL has no colour device.

## Gotchas

* WSL: write a script, run `MSYS_NO_PATHCONV=1 wsl -d Ubuntu-24.04 -- bash
  /mnt/c/...`.  Python in Git Bash is the Windows one
  (`/c/Users/spam/AppData/Local/Programs/Python/Python39/python`, also
  `python3`): **its text mode writes CRLF** -- open files `'wb'`/`'rb'` when
  editing, or shell scripts stop running in WSL.  m68k objdump:
  `/home/dani/opt/m68k/usr/bin/m68k-linux-gnu-objdump`; poppler (pdftoppm,
  pdfinfo) under `/home/dani/opt/poppler/root/usr/bin` with
  `LD_LIBRARY_PATH=.../usr/lib/x86_64-linux-gnu`.  The ARM toolchain for Main
  is `/opt/gcc-arm-10.2-2020.11-x86_64-arm-none-linux-gnueabihf`; build Main
  from a copy (`git archive`), never in the user's checkout.
* The checkout is CRLF (`core.autocrlf=true`): `sed` anchors miss `\r`.  A
  Python heredoc in the Bash tool loses `\\`; edit Makefile recipes with the
  Edit tool.  Verilator keeps a function's local queue between calls inside a
  loop -- clear it by hand.
* `rtl/vendor/*` are unmodified upstream copies; `rtl/patched/` holds the one
  patched file.
* Board: check `/tmp/CORENAME` before typing; `/tmp` is empty after a reboot
  (copy `tools/mister_keys.py` back).  `|` is Return, `{PIPE}` a pipe, `{^G}`
  a control key; `{M dx dy}`, `{ML}`/`{MR+}`/`{MR-}` the mouse -- keep a press
  and its release in one run.  Typing before `login:` is thrown away.
  Screenshots don't show the OSD; they are 1160x904 at 1080p.  The network
  mailbox can be read from Linux through `/dev/mem` at 0x1FF00000.
* Halting a disk whose root password is unknown: log in as `sync` (flushes),
  then L1-A (`!` in mister_keys).  Both board disks currently let root in with
  no password.
* Loading a core through an MGL changes the remembered disk
  (`config/Sun-2.s0`); the OSD's options are `config/Sun-2.CFG` (16 bytes of
  status).
* `Reboot failed...help!` on `/usr`: `umount /usr`, `fsck -y /dev/rsd0g`,
  `reboot` (never `sync`/halt there).
* SunOS facts: the Sun-2 disk ceiling is 1 GiB; 4.0.3 tapes are upgrade-only;
  `times()` is in sixtieths; a user bus error is always SIGSEGV; a standalone
  install names the machine 127.0.0.1 in `/etc/hosts`; ftpd refuses root
  without a password.
* A running Main cannot be overwritten (`Text file busy`): copy the new one to
  `/media/fat/MiSTer.new` and `mv` it over `MiSTer`, keep the old one as
  `MiSTer.<commit>`, then `sync` and `reboot`.
* The network's mailbox from the MiSTer's Linux: `mmap` `/dev/mem` at
  0x1FF00000 from python3 and read the 64-bit words -- magic, GEN, TX_WPTR,
  TX_RPTR, RX_WPTR, RX_RPTR, MAC (layout in `rtl/sun2_mister_enet.sv`).  A
  pointer pair that moves together is traffic both sides took.
* Testing the network without changing a disk: the 1 GB disk's telnetd lets
  root in, so Python's `telnetlib` from this PC (192.168.99.82; gateway .1; the
  Sun at .236, set by hand with `ifconfig ie0`) can push a file in through
  `uudecode` and pull it out with `uuencode`, compared with SunOS `sum` (BSD:
  rotate right one bit, add the byte).  Write end markers as `MARK""X`, or the
  pty's echo of the command line matches before the output arrives.  SunOS's
  own `ping` stops at 2048 bytes: send the big ones from the PC.  This SunOS
  answers ping with TTL 128, which looks like Windows and is not.
